# rag-interface — NGO Knowledge Assistant (RAG demo)

## What this is
A local RAG pipeline for a fictional NGO ("Cedar Health Alliance") knowledge
assistant. This is Project 1 of a two-project portfolio build for Haithem's
freelance "AI Integration Consultant" business, meant to demonstrate real
agentic-AI production skills for client work and interviews.

## Current architecture
- **Backend**: FastAPI (`app.py`), single `/api/chat` endpoint
- **Retrieval**: sentence-transformers (`all-MiniLM-L6-v2`) embeddings,
  indexed in ChromaDB. NOTE: `chromadb.Client()` is in-memory only —
  re-embeds and re-indexes all PDFs from `documents/` on every server
  restart. Not yet persisted to disk.
- **Ingestion**: 25 synthetic policy PDFs in `documents/`, generated by
  `make_pdfs.py` from the data in `mock_docs.py` (via reportlab)
- **Generation**: agent loop in `chat()` calling `claude-sonnet-5` via the
  `anthropic` Python SDK with three tools (`retrieve_documents`, `calculate`, `web_search`),
  capped at `MAX_ITERATIONS`.
- **Frontend**: static chat UI (`static/index.html`), vanilla JS hitting
  the one endpoint
- **Secrets**: `ANTHROPIC_API_KEY` loads from `.env` via `python-dotenv`
  (previously hardcoded in `app.py` — fixed). `.env` is gitignored.
  No `.git` repo initialized yet.

## Project 1 roadmap: "Agentic AI with Production Protocols"
Goal: extend this RAG demo into a small but genuine agent system, real
enough to describe concretely in an interview — deployed the way a real
production system would be.

1. **Agents & Tool Use (Function Calling)** — DONE
   - Tools: `retrieve_documents` (RAG) and `calculate` (AST-whitelist
     evaluator, no eval()). Brave web search is added in step 2.
   - Native Anthropic tool-use API, no framework; bounded
     plan → act → observe loop (`MAX_ITERATIONS`), tool errors returned to
     Claude as `tool_result` text so it can retry.
2. **Integration Plumbing (APIs, webhooks, no-code)** — DONE
   - (a) Brave Search API tool `web_search`: auth header
     (`X-Subscription-Token`), 429 handling (one capped retry using
     X-RateLimit-Reset), 10s timeout, per-failure-type error messages.
     Verified live through the agent by the `external-web` eval case.
   - (b) `POST /api/webhook/ask`, shared secret in `X-Webhook-Secret`
     (`WEBHOOK_SECRET` in `.env`, `hmac.compare_digest`). Agent loop lives
     in `run_agent()`, shared with `/api/chat`. HMAC body signing = possible
     upgrade.
   - (c) Local n8n (`N8N_SECURE_COOKIE=false npx n8n`, UI at localhost:5678):
     Manual Trigger -> HTTP Request to `http://127.0.0.1:8000/api/webhook/ask`
     (127.0.0.1, not localhost: app listens on IPv4 only).
3. **Prompt Engineering as a Discipline** — DONE
   - `prompts/v0.txt`, `v1.txt`, `v2.txt` (selected via `PROMPT_VERSION`), reasoning
     and caveats in `prompts/CHANGELOG.md`. v2 is the app default; set
     PROMPT_VERSION to compare other versions.
4. **Evaluation & Reliability** — DONE
   - `evals/run_evals.py` + `evals/cases.json` (19 cases), results in
     `evals/results/`. Structured JSON tool-call logging, `truncated` detection.
     Known gaps listed in `prompts/CHANGELOG.md`.
5. **GDPR / Data Privacy Basics** — not started
   - Data-flow documentation, redaction step before external calls
     (relevant here: the mock policy docs simulate sensitive
     clinical/patient-adjacent content, so this is a real design
     consideration, not just a checkbox)
6. **Containerization & Deployment (Docker + basic CI/CD)** — BUILT, GitHub push pending
   - Done locally: `Dockerfile` (python 3.12-slim, CPU torch, model baked in,
     non-root, HEALTHCHECK, image ~2.7GB), `.dockerignore`, `/api/health`,
     per-request JSON logs, `.github/workflows/ci.yml` (build, smoke test,
     evals inside the image). Container verified: healthy, chat + webhook work.
     CI workflow has NOT run on GitHub yet; needs repo push + Actions secrets
     `ANTHROPIC_API_KEY` and `BRAVE_API_KEY` (set by the user).
   - Dockerfile for the agent app (buildable container is the deliverable)
   - Basic CI/CD (GitHub Actions): on push, run the eval harness and build
     the Docker image
   - Health-check endpoint + basic structured logging
   - Explicitly out of scope: Kubernetes, multi-node scaling, cloud
     deployment (Azure/AWS/GCP)
   - GitHub is only needed for this step specifically (to have something
     for CI to run against); everything else can be built/demoed locally

Deliverable: a working, deployed artifact with a short architecture
write-up covering the containerized deployment, CI/CD, and eval results.
